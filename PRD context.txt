Você vai implementar, no backend `server-mei`, a API fiscal que o app Android **Caltech MEI** já
consome. O app está pronto e testado contra o contrato abaixo. Seu trabalho é fazer o servidor
falar **exatamente** este contrato: mesmos caminhos, mesmos nomes de campo, mesmos valores de
enum, mesmos tipos. Onde este documento diz "PERGUNTE", pare e pergunte ao responsável. Nunca
invente.

Leia o documento inteiro antes de escrever código.

## 0. O que esta tarefa entrega e o que ela NÃO consegue entregar sozinha

## 1. Regras inegociáveis

1. HTTPS sob `/api/v1/fiscal`. Autenticação **Bearer** real (ver seção 2). O tenant (empresa) vem
   **só do token**. Header ou campo enviado pelo cliente nunca dá acesso a outra empresa.
2. `Idempotency-Key` é obrigatório em `POST /documents`. Ele é único por tenant + operação +
   payload canônico. A mesma chave com o mesmo payload devolve **a mesma** operação (mesmo `id`).
   A mesma chave com payload diferente devolve `409` com código estável `IDEMPOTENCY_CONFLICT`.
3. Certificado A1 e senha chegam só em `POST /certificates`. A senha é descartada logo após a
   importação. O PFX fica **cifrado em cofre de segredos** (KMS/Vault ou equivalente), nunca em
   coluna de banco em texto puro e nunca em log.
4. Logs nunca contêm: XML, certificado, senha, CSC, CPF/CNPJ completo, endereço ou URL assinada.
   Use `correlationId` em todo log.
5. XML autorizado e XML de eventos são **imutáveis**, cifrados em repouso, auditados e com
   backup. Nunca sobrescreva XML autorizado.
6. Dinheiro e quantidade são **strings decimais** no JSON (ex.: `"80.00"`, `"0.250"`). No servidor
   use tipo decimal exato (`BigDecimal`/`Decimal`/`NUMERIC`). **Proibido float/double.**
7. Datas e horas: string **ISO-8601 em UTC** (ex.: `"2026-11-09T18:30:00Z"`). Exceção já usada pelo
   app: os campos de `classification` são **epoch em milissegundos** (`Long`).
8. **Nunca invente** regra fiscal: alíquota, CFOP, NCM, CST/CSOSN, código de tributação, regra por
   UF, município, XSD, URL de autorizador. Tudo vem de fonte oficial versionada no backend. Se a
   informação não estiver disponível, devolva rejeição de negócio clara (seção 6) e registre a
   pendência.
9. `AUTHORIZED` só pode ser devolvido com **todas** as evidências oficiais (seção 7). HTTP 200 sozinho
   não autoriza nada; o app rejeita `AUTHORIZED` incompleto.

## 2. Autenticação — mudança coordenada com o app (LEIA)

Hoje o app envia em toda chamada só o header `validation-uuid: <uuid da empresa>`, sem token. Isso
**não pode** autorizar operação fiscal (qualquer um com o UUID emitiria nota em nome da empresa).

Implemente:
- login que devolve **JWT** (ou token opaco) com `sub` = usuário e o tenant = empresa;
- todas as rotas `/api/v1/fiscal/*` exigem `Authorization: Bearer <token>`. Sem token ou com token
  inválido: `401`. Token válido para empresa diferente do recurso: `404` (não vaze existência);
- o header `validation-uuid` é **ignorado** nas rotas fiscais (pode continuar nas rotas antigas).

PERGUNTE ao responsável qual é o fluxo de login atual (`AuthApi`) antes de mudar a resposta dele,
e documente o formato final (endpoint, campo do token, expiração, refresh). O app vai precisar de
uma atualização para enviar o Bearer; até lá, as rotas fiscais responderão `401` e o app cai no
canal oficial (comportamento seguro e já testado).

## 3. Convenções de JSON (compatibilidade com o app)

- O app usa **Gson**. Ao **enviar**, campos `null` são **omitidos** do JSON. Trate campo ausente
  como `null`.
- Ao **receber**, todo campo marcado como obrigatório abaixo deve vir **sempre presente e não
  nulo**. Campos opcionais podem ser `null` ou ausentes. Campos extras são ignorados pelo app
  (pode acrescentar campos, nunca renomear nem remover).
- Booleans são `true`/`false` JSON; enums são strings em MAIÚSCULAS exatamente como listadas.
- Corpo de erro (todas as respostas 4xx/5xx):
  ```json
  { "code": "CODIGO_ESTAVEL", "message": "texto em pt-BR para o usuário", "correlationId": "..." }
  ```

### 4.1 `GET /config` → `200`
```json
{
  "nfseEnvironment": "RESTRICTED_PRODUCTION",
  "nfeEnvironment": "RESTRICTED_PRODUCTION",
  "productionEnabled": false,
  "provider": "SEFIN_NACIONAL",
  "lastValidatedAt": "2026-11-09T18:30:00Z"
}
```
Obrigatórios: `nfseEnvironment`, `nfeEnvironment` (`RESTRICTED_PRODUCTION` | `PRODUCTION`),
`productionEnabled`. Opcionais: `provider`, `lastValidatedAt`. O app trata ambiente desconhecido
como `RESTRICTED_PRODUCTION` e recusa `PRODUCTION` se `productionEnabled=false`.

### 4.2 `GET /capabilities?uf=SP` → `200`
```json
{
  "uf": "SP",
  "version": "2026.11.09-1",
  "nfseAutomatic": true,
  "nfce": false,
  "nfe": true,
  "nffOfficialChannel": false,
  "requiresCertificate": true,
  "reason": null,
  "nfseUnidentifiedRecipientAllowed": false,
  "stateOfficialChannelUrl": "https://<emissor-oficial-da-sefaz>.gov.br/..."
}
```
- Obrigatórios: `uf`, `version` (não vazio; versão das regras usadas), `nfseAutomatic`, `nfce`,
  `nfe`, `nffOfficialChannel`, `requiresCertificate`. Opcionais: `reason` (pt-BR),
  `nfseUnidentifiedRecipientAllowed`, `stateOfficialChannelUrl`.
- `uf` ou `version` vazios fazem o app **bloquear** a emissão. Devolva valores reais.
- `nfseAutomatic=true` **somente** se o tenant estiver credenciado e o adaptador NFS-e estiver
  operacional naquele ambiente. `nfe`/`nfce` idem, por UF e por tenant.
- `nffOfficialChannel=true` só quando a UF/cadastro do tenant aceitar a Nota Fiscal Fácil (NFF).
  Com `true`, o app manda o produto **para a NFF** (não emite NF-e/NFC-e pelo app).
- `stateOfficialChannelUrl`: endereço oficial do emissor da SEFAZ da UF. O app só abre se for
  `https` em domínio `*.gov.br`. Não sabe a URL oficial? Mande `null`. **Não invente.**
- Os valores por UF vêm de tabela versionada no backend, alimentada por fonte oficial.

### 4.3 `GET /certificates/status` → `200`
```json
{
  "configured": true,
  "valid": true,
  "certificateId": "cert_01H...",
  "holder": "EMPRESA EXEMPLO LTDA:12ABC34501DE35",
  "expiresAt": "2027-06-30T23:59:59Z",
  "type": "A1",
  "lastValidatedAt": "2026-11-09T18:30:00Z",
  "holderTaxId": "12ABC34501DE35"
}
```
- Obrigatórios: `configured`, `valid`. Sem certificado: `configured=false`, `valid=false`, demais
  `null`.
- `valid=true` só se: cadeia ICP-Brasil válida, não revogado, dentro da validade, tipo A1 e CNPJ do
  titular **igual** ao CNPJ do tenant.
- `holderTaxId`: CNPJ do titular lido do OID ICP-Brasil **2.16.76.1.3.3** do SubjectAltName
  (otherName), só letras/dígitos, maiúsculo. **Aceite CNPJ alfanumérico** (IN RFB 2.229/2024; DV
  em módulo 11 com valor de cada caractere = código ASCII − 48; exemplo oficial
  12.ABC.345/01DE-35).
- `expiresAt` em UTC. O app converte para a data de São Paulo.

### 4.4 `POST /certificates` (multipart/form-data) → `200` com o mesmo corpo do 4.3
- Part `certificate`: arquivo (`filename="certificado.pfx"`, `Content-Type: application/x-pkcs12`),
  até 64 KB.
- Part `password`: `text/plain`, UTF-8.
- Valide como no 4.3. Rejeições: `422` com `code` em `CERTIFICATE_WRONG_PASSWORD`,
  `CERTIFICATE_EXPIRED`, `CERTIFICATE_NOT_A1`, `CERTIFICATE_HOLDER_MISMATCH`,
  `CERTIFICATE_REVOKED`, `CERTIFICATE_INVALID`. O app trata qualquer HTTP de erro como "servidor
  recusou" e um `200` com `configured && valid` como sucesso; `200` sem isso vira "ainda não ativo".
- Zere a senha da memória após a importação. Grave só o PFX cifrado no cofre e os metadados.
  Substituir certificado: o novo só passa a valer depois de validado; o antigo é revogado no cofre.

### 4.5 `DELETE /certificates/{id}` → `204`
Remoção auditada. Documentos já autorizados continuam intactos.

### 4.6 `POST /documents` → `202` (ou `200` em repetição idempotente) com `FiscalDocumentDto`
Header obrigatório: `Idempotency-Key: <uuid gerado pelo app>`.

Corpo comum (`CreateFiscalDocumentRequest`):

**Serviço (NFS-e), `schemaVersion = "1.2"`:** `documentType=NFSE`, `operation=null`,
`product=null`, `items=[]`, `payments=[]`.

### 4.9 Cancelamento e retentativa
- `POST /documents/{id}/cancel` com `{ "reason": "motivo com o tamanho mínimo exigido pelo leiaute" }`
  → documento em `CANCEL_PENDING` e depois `CANCELLED`, só com evento oficial homologado.
  Fora do prazo ou não autorizado: `422` com código estável.
- `POST /documents/{id}/retry`: só para `ERROR_RETRYABLE`. Nunca retransmita sem antes consultar o

### 4.10 Downloads
`/xml` → `application/xml`; `/auxiliary-document` → `application/pdf`. Autenticados a cada
chamada (ou URL temporária curta). Só para documentos `AUTHORIZED`/`CANCELLED`; senão `404`.
O DANFSe/DANFE é o oficial (ou gerado pelo leiaute oficial a partir do XML autorizado), nunca um
PDF "de mentira".

## 5. Processamento

1. `POST /documents`: autentica, valida sintaxe e regras, grava a intenção com a
   `Idempotency-Key`, devolve `202` com `status=QUEUED` (ou `VALIDATING`). Não bloqueie a
   requisição esperando o órgão.
2. Worker: reserva série/número de forma **atômica** por emitente + ambiente + modelo; monta o
   XML no leiaute oficial vigente; valida no XSD; assina XMLDSig com o e-CNPJ do cofre; transmite
   por mTLS; grava a resposta oficial.
3. Timeout ambíguo após transmitir: consulte o órgão (para NFS-e, `GET /dps/{id}`; para NF-e/NFC-e,
   a consulta de protocolo/situação) **antes** de qualquer retransmissão.
4. Fila com backoff + jitter só para erro temporário. Toda transição gera auditoria com
   `correlationId`, sem payload sensível.
5. Adaptadores NFS-e e NF-e/NFC-e separados do domínio.

**NFS-e para MEI:** integração **exclusiva** com a SEFIN Nacional (nunca emissor municipal):
- Produção restrita: `https://sefin.producaorestrita.nfse.gov.br/API/SefinNacional`
- Produção: `https://sefin.nfse.gov.br/SefinNacional`

Passos: obter do tenant CNPJ, município IBGE e regime MEI; consultar e manter com prazo curto os
parâmetros oficiais do município e do serviço; reservar número da DPS; montar a DPS no leiaute
vigente; validar no XSD; assinar; compactar em GZip e codificar em Base64 no envelope JSON oficial;
`POST /nfse` por mTLS; validar e persistir XML, chave, número, código de verificação e resposta.
O `nationalTaxCode` é confirmado contra os parâmetros oficiais, não inferido do CNAE. ISS,
retenções, local de incidência e IBS/CBS vigentes são validados **no backend**. Use a documentação
técnica oficial vigente do Sistema Nacional NFS-e (confira a versão no portal oficial antes de
começar e registre-a; não use versão de memória).

**NF-e 55 / NFC-e 65:** autorizador da UF do tenant, URLs e leiaute conforme o Portal Nacional da
NF-e e a SEFAZ da UF (versionados no backend). NFC-e exige CSC/ID CSC no cofre. Contingência só a
prevista no leiaute. Não implemente NFF por API: ela é emitida pelo próprio MEI no portal oficial.

## 6. Respostas de erro (códigos estáveis)

| HTTP | Quando | `code` (exemplos) |
|---|---|---|
| 400 | JSON malformado, header faltando | `BAD_REQUEST`, `IDEMPOTENCY_KEY_REQUIRED` |
| 401 | sem token / token inválido | `UNAUTHENTICATED` |
| 404 | recurso não existe para este tenant | `NOT_FOUND` |
| 409 | idempotência, capability mudou | `IDEMPOTENCY_CONFLICT`, `CAPABILITY_CHANGED` |
| 422 | regra de negócio | `PRODUCTION_DISABLED`, `CERTIFICATE_REQUIRED`, `RECIPIENT_REQUIRED`, `NCM_INVALID`, `CFOP_INCOHERENT`, `TOTALS_MISMATCH`, `FISCAL_REVIEW_REQUIRED`, ... |
| 429 | limite de taxa | `RATE_LIMITED` |
| 503 | órgão/adaptador indisponível | `UPSTREAM_UNAVAILABLE` |

Rejeição **do órgão** depois de transmitir não é erro HTTP: o documento vai para `REJECTED` com
`fiscalErrorCode`/`fiscalErrorMessage`.

## 7. `AUTHORIZED` válido (o app confere)

Só devolva `status=AUTHORIZED` com **todos** preenchidos e coerentes: `environment`, `documentType`,
`series`, `number`, `officialKey` (chave/identificador oficial), `protocol`, `authorizedAt` (UTC),
`xmlSha256` (64 caracteres hexadecimais minúsculos, SHA-256 do XML autorizado armazenado) e
`xmlArtifactId` (referência do XML para download). Faltou algum: o app trata como não autorizado.

## 9. Testes obrigatórios (critério de pronto)

Automatizados (sem transmitir em produção; use produção restrita/homologação ou dublês):
1. Contrato: cada JSON de exemplo deste documento é aceito/devolvido exatamente (nomes, tipos,
   enums, campos obrigatórios presentes e não nulos).
2. Multi-tenant: token da empresa A nunca lê, cria ou baixa nada da empresa B; `validation-uuid`
   ignorado.
3. Idempotência: mesma chave + mesmo payload → mesmo `id`; payload diferente → `409`; 20 requisições
   concorrentes com a mesma chave → 1 documento.
4. Certificado: senha errada, vencido, não A1, titular diferente (inclusive CNPJ alfanumérico),
   revogado, válido; a senha não aparece em log nem em banco.
5. NFS-e em produção restrita: autorização, rejeição, timeout com reconciliação, cancelamento.
6. NF-e/NFC-e em homologação: autorização, rejeição, timeout, cancelamento, contingência aplicável.
7. `AUTHORIZED` só com evidências completas; XML imutável; `xmlSha256` confere com o arquivo.
8. Decimal: nenhum float/double em dinheiro; arredondamentos conferidos.
9. Logs: varredura automática garante que não há CPF/CNPJ completo, XML, senha ou certificado.
